Sudoers / less CTF — Deep Walkthrough

Linux escalation — sudoers (Medium). A sudo rule lets less run as another account, and less can open a shell.

ChallengeLinux Escalation — sudoers (Medium)
Initial accountuser
Privilege targetctf
Scope. This document covers only the first authorized CTF discussed in the session. It explains the observed SSH access and the sudo/less privilege transition. The session did not capture the later ctf-to-root step, so this walkthrough does not invent one.

1. Understanding the provided challenge files

The challenge package contained two important files: username.txt and id_ecdsa. The username file contained user, while id_ecdsa was an ECDSA SSH private key.

An SSH private key is authentication material. Instead of entering an account password, the SSH client can prove possession of the private key corresponding to a public key authorized on the server.

2. Why the initial netcat attempt failed

The first connection attempt used netcat:

nc 172.31.45.248 31711

The server replied:

SSH-2.0-OpenSSH_8.2p1 Ubuntu-4ubuntu0.1

After typing ls, the response was:

Invalid SSH identification string.

This happened because TCP port 31711 was not a raw command shell. It was an SSH service. Netcat established a TCP connection and exposed the SSH banner, but it did not perform the SSH protocol handshake. Sending ls therefore looked like invalid SSH protocol data to the server.

The important lesson is: a reachable TCP port is not automatically an interactive shell. First identify the protocol running on it, then use the correct client.

3. Preparing the SSH private key

OpenSSH expects private key files to have restrictive local permissions. The key was protected with:

chmod 600 id_ecdsa

Mode 600 means:

6 = read + write for the owner
0 = no permissions for the group
0 = no permissions for others

Result: rw-------

This protects the private key from other local users and prevents the SSH client from rejecting it as overly accessible.

4. Connecting correctly with SSH

ssh -i id_ecdsa -p 31711 user@172.31.45.248
PartMeaning
sshStart the OpenSSH client.
-i id_ecdsaUse id_ecdsa as the private identity key.
-p 31711Connect to SSH on non-default TCP port 31711.
user@Authenticate as the account named user.
172.31.45.248Challenge target address.

5. Enumerating sudo permissions

Once logged in, the key enumeration command was:

sudo -l

sudo -l lists the commands that the current account is permitted to execute through sudo. In privilege-escalation labs this is important because a program that looks harmless may expose functionality capable of starting another process or shell.

The challenge returned:

Matching Defaults entries for user:
    env_reset, mail_badpass,
    secure_path=/usr/local/sbin:/usr/local/bin:/usr/sbin:/usr/bin:/sbin:/bin:/snap/bin

User user may run the following commands:
    (ctf : ctf) NOPASSWD: /usr/bin/less

6. Deep meaning of the sudo rule

The critical line was:

(ctf : ctf) NOPASSWD: /usr/bin/less

It does not say that user can run less as root. The first ctf is the permitted run-as user, and the second ctf is the permitted run-as group. NOPASSWD means sudo will not request a password for this allowed command. /usr/bin/less is the exact permitted executable.

Current identity: user
       |
       | sudo rule permits /usr/bin/less
       v
Run-as identity: ctf:ctf

This is why blindly using sudo less ... is less clear than explicitly specifying -u ctf: the objective is to exercise the permission exactly as the sudo rule describes.

7. What /etc/hosts is and why it was used

/etc/hosts is a normal Linux text configuration file used for local hostname-to-IP mappings. A simple example could contain:

127.0.0.1   localhost
192.168.1.50 server1

In this CTF, /etc/hosts was not the vulnerability. It was simply a convenient readable text file to give to less. The command needs a file to display so that the interactive less interface opens.

The path can be read as:

/etc/hosts
 |    |
 |    +-- file named hosts
 +------- /etc, the system configuration directory

8. Running less as the ctf account

sudo -u ctf /usr/bin/less /etc/hosts
PartMeaning
sudoExecute an allowed command through sudo
-u ctfRequest ctf as the run-as user
/usr/bin/lessThe exact program allowed by sudoers
/etc/hostsReadable text file opened by less

At this point the important security context is that the less process itself is running with ctf's identity.

9. Why less can become a privilege-escalation primitive

less is an interactive pager, not merely a passive file reader. Its interactive command interface supports invoking an external shell command using !. If a privileged sudo configuration allows less without preventing that functionality, a command launched from inside less can inherit the identity of the privileged less process.

Inside the running less interface, the challenge used:

!/bin/bash

Conceptually:

user
 |
 | sudo -u ctf /usr/bin/less /etc/hosts
 v
less process running as ctf
 |
 | !/bin/bash
 v
bash process inherits ctf identity
 |
 v
ctf shell

The security mistake is therefore not that /etc/hosts can be read. The problem is granting a more privileged identity permission to run an interactive program capable of spawning external commands.

10. Verifying the new identity

After the shell opened, the identity should be verified rather than assumed:

whoami
id

whoami prints the effective username. id gives more detail, including UID, primary GID, and supplementary groups. A successful first transition should show the ctf identity.

11. Enumerating the next privilege boundary

After becoming ctf, the next correct step is to enumerate sudo permissions again:

sudo -l

Why repeat it? Sudo policy is evaluated for the current account. The permissions available to ctf may be completely different from those available to user. Therefore each privilege transition creates a new enumeration point.

Where the verified walkthrough stops. The conversation ended before the output of this second sudo -l was captured. For accuracy, this walkthrough stops the verified path here instead of fabricating the ctf-to-root method.

13. Root cause

The verified sudoers weakness is an unsafe delegation of an interactive executable. The low-privileged account was intentionally allowed to execute less as another account, but less includes functionality that can launch external commands. Consequently, the permission effectively delegated more capability than simply viewing a file.

A safer sudo policy should grant the narrowest possible non-interactive operation, avoid shell-capable programs where unnecessary, and use application-specific restrictions or dedicated helpers when privileged file viewing is required.

14. Commands used in the verified first CTF

# Initial test that revealed SSH was running on the port
nc 172.31.45.248 31711

# Protect the provided private key
chmod 600 id_ecdsa

# Correct SSH login
ssh -i id_ecdsa -p 31711 user@172.31.45.248

# Enumerate current sudo permissions
sudo -l

# Run the allowed pager as ctf
sudo -u ctf /usr/bin/less /etc/hosts

# Type this INSIDE less, not at the normal shell prompt
!/bin/bash

# Verify the resulting identity
whoami
id

# Enumerate the new account's sudo permissions
sudo -l

15. Main learning points

First, identify the service protocol before interacting with a port. Second, treat sudo -l as a privilege-boundary map rather than assuming sudo always means root. Third, read the run-as user and group carefully. Fourth, recognize that interactive tools such as pagers, editors, interpreters, and similar programs may expose command-execution features. Finally, after every successful identity transition, verify the identity and enumerate again.
