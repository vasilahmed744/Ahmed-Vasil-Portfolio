1. Objective and attack path

The goal was not to guess an exploit immediately. The correct workflow was to enumerate privileged executables, identify an unusual permission assignment, prove the privilege transition, discover which resources that privilege could access, and only then use the privileged execution context.

2. SUID and SGID — what the permission bits mean

SUID (Set User ID) causes an executable to run with the effective user identity of the file owner. SGID (Set Group ID) on an executable causes it to run with the effective group identity of the file's group owner.

The vulnerable entry in this lab was:

-rwxr-sr-x 1 root ctf 320160 Feb 18 2020 /usr/bin/find

The important character is the s in the group execute position. The owner is root, the group is ctf, and the SGID bit means execution can obtain the effective group ID of ctf. This is different from a root-SUID binary: it does not automatically make the user root.

3. Enumeration

3.1 Enumerate SUID files

find / -type f -perm -4000 -ls 2>/dev/null

This produced many normal system SUID binaries. Nothing should be exploited simply because it has SUID; standard entries must be distinguished from unusual or challenge-specific permissions.

3.2 Enumerate both SUID and SGID

find / -type f \( -perm -4000 -o -perm -2000 \) -ls 2>/dev/null

This wider search exposed the important entry:

-rwxr-sr-x 1 root ctf 320160 Feb 18 2020 /usr/bin/find

Why it stood out: find was assigned SGID to a challenge-specific group named ctf. Since find also supports -exec, commands launched through it became especially interesting to test.

4. Proving the privilege transition

4.1 Check the normal identity

id
uid=1001(user) gid=1002(user) groups=1002(user)

The account was not a member of the ctf group under its normal identity.

4.2 Execute id through the SGID binary

find / -maxdepth 0 -exec id \;
uid=1001(user) gid=1002(user) egid=1001(ctf) groups=1001(ctf),1002(user)

This was the decisive proof. The real UID remained user and the normal GID remained user, but the effective GID changed to ctf. Therefore, child commands executed by this SGID context could potentially use permissions granted to the ctf group.

Key lesson: do not assume a permission misconfiguration is exploitable. First prove what effective identity the process actually receives.

5. Finding what the new privilege can access

Once egid=ctf was confirmed, the next question was: what files or directories are accessible to the ctf group that the normal user cannot access?

find /home -group ctf -ls 2>/dev/null

Relevant output:

drwxr-x--- 2 root ctf 4096 ... /home/ctf
-r--r----- 1 root ctf   38 ... /home/ctf/flag

The flag permissions were -r--r-----. Root had read permission, the ctf group also had read permission, and everyone else had no permission. The directory itself also permitted access to the ctf group.

6. Validate the access control failure

6.1 Direct read as the normal user

cat /home/ctf/flag
cat: /home/ctf/flag: Permission denied

This failure was expected and useful. It proved that the normal account could not simply read the protected file.

6.2 Read through the SGID find execution context

find /home/ctf/flag -exec cat {} \;
ctf{ai3ooph4yaiYiquie7Ahr6chaequahru}

The same cat operation succeeded when launched through SGID find, because the execution context had effective group ctf. The ctf group had read permission on the flag, so the kernel allowed the read.

Flagctf{ai3ooph4yaiYiquie7Ahr6chaequahru}

7. Why the exploit works

Normal path:
user -> cat -> /home/ctf/flag
GID = user
Result: Permission denied

Privileged path:
user -> SGID /usr/bin/find -> -exec cat -> /home/ctf/flag
                           |
                           +-> Effective GID = ctf
Result: Read permitted by the file's group permission

The vulnerability is therefore an SGID binary misconfiguration. The dangerous combination is not merely that SGID exists; it is that a powerful utility capable of executing arbitrary commands was assigned a privileged group identity whose resources should not be available to the unprivileged user.

8. How to discover this without a walkthrough

A reusable Linux privilege-escalation methodology is:

  1. Establish identity — id, whoami, groups and current access.
  2. Enumerate privileged execution — sudo -l, SUID/SGID binaries, file capabilities, cron/timers and privileged services.
  3. Identify anomalies — look for custom paths, unusual group owners, unexpected SUID/SGID on powerful utilities, writable inputs and executables.
  4. Understand behavior — check help, permissions, file type and what commands/files the program can invoke or access.
  5. Prove the transition — run a harmless identity check such as id through the suspected mechanism.
  6. Map privilege to resources — search for files/directories owned by or accessible to the newly obtained user/group.
  7. Validate normal denial — confirm the resource is not already accessible with the original identity.
  8. Use the minimum needed — exercise the privileged context only enough to access the intended protected resource.

# File capabilities
getcap -r / 2>/dev/null

# Group-owned resources after discovering an interesting group
find /home -group ctf -ls 2>/dev/null
find / -group ctf -ls 2>/dev/null

# Prove SGID behavior in this lab
find / -maxdepth 0 -exec id \;

10. Remediation

The unnecessary SGID permission should be removed from /usr/bin/find. A standard system utility capable of executing other commands should not carry an unrelated privileged group identity.

chmod g-s /usr/bin/find
ls -l /usr/bin/find

Administrators should also audit SUID/SGID assignments regularly, restrict sensitive group membership and group-readable resources, and investigate why a general-purpose command-execution utility received the ctf group's privilege in the first place.
